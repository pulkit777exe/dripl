# Dripl codebase audit and Excalidraw parity report

**Audit date:** 2026-09-25  
**Baseline:** stable `@excalidraw/excalidraw` v0.18.1 / Excalidraw public app and first-party repository sources  
**Scope:** current uncommitted Dripl workspace, including the security, collaboration, persistence, AI, UI/UX, export, and performance changes in this working tree. Primary Excalidraw source links and package-vs-hosted-app distinctions are recorded in [`docs/excalidraw-feature-baseline.md`](./excalidraw-feature-baseline.md).

**Inventory provenance:** This documentation-inventory pass inspected source,
manifests, and test files; it did not independently rerun the command results,
services, browser flows, or external providers recorded below.

## Executive conclusion

Dripl is now a credible broad-canvas implementation, not an Excalidraw-compatible or production-ready clone. The current tree has substantially stronger authorization, schema validation, persistence race handling, collaboration lifecycle handling, AI input controls, and test evidence than the baseline audit. It still has material gaps in advanced editor behavior, true CRDT/E2EE collaboration, production-backed integration evidence, and operational deployment validation.

**Current overall grade: C+ / 7.0/10 (evidence-weighted, not a launch or A+ claim).**

The grade is deliberately capped. Passing unit tests, a successful TypeScript build, and a successful Next build do not establish production readiness. A disposable local PostgreSQL 16 migration/smoke/HTTP integration run was completed, but there is still no production/remote PostgreSQL, Redis, Gemini credential, or browser session in this audit workspace. The opt-in production WebSocket process test uses two real `ws` clients but mocks ticket validation and persistence; it is not a database-backed deployment test. A second opt-in suite now does run two real clients against a real migrated PostgreSQL, and that one is database-backed but still stubs the HTTP ticket exchange.

### Grade scale

- **A+:** production-ready, complete against the stated scope, independently exercised, measured, and monitored.
- **A:** strong implementation and evidence with only low-risk residual gaps.
- **B:** solid integrated implementation with meaningful but bounded gaps.
- **C:** useful implementation/prototype with important correctness, integration, or evidence gaps.
- **D:** partial or unsafe implementation; not suitable for production reliance.
- **F:** missing, fundamentally broken, or unmaintainable.

Grades below are **current-tree grades**, not guarantees about unreviewed production infrastructure.

## Security posture

### Improvements with code/test evidence

- JWT verification is restricted to HS256 and server-issued sessions are verified server-side; AI identity claims are ignored.
- AI requests enforce origin checks, prompt/body bounds, bounded model output, schema normalization, authenticated per-user rate limits, bounded Gemini retries/timeouts, and propagate the incoming abort signal to the SDK request.
- WebSocket joins validate short-lived tickets, room/file authorization, viewer mutation rejection, message schemas, numeric bounds, cursor-color validation, deduplication, version/nonce ordering, per-mutation and passive authorization refresh, bounded byte/count queues, duplicate-connection rejection, and serialized per-connection message handling. Shared element style colors are length-bounded but are not regex-validated like the dedicated cursor color field.
- File writes validate scene structure and use optimistic `updatedAt` conflict checks; encrypted share snapshots and app state survive later owner/WS saves, stale WS saves are fenced by the loaded database timestamp, final-element deletions can be saved on leave/GC/shutdown, metadata-read failures abort rather than erase an encrypted share envelope, and the browser autosave refreshes a safe conflict fence or pauses with an explicit reload action.
- Image uploads require auth, validate content signatures, generate narrow IDs, reject traversal-shaped IDs, and disallow SVG content.
- CORS/WS origin configuration accepts normalized comma-separated origins and rejects prefix lookalikes.
- Local rate-limit maps are bounded and evict oldest active identities; `Retry-After` is returned for rejected requests.
- Database TLS verification remains enabled by default; insecure remote TLS is an explicit non-production opt-in.
- Docker build stages now build backend/frontend artifacts after copying their source, and the interactive postinstall approval prompt was removed.

### Security blockers and caveats

1. **No production security/operations test:** the disposable local PostgreSQL integration run is not a production security test; no production secrets, Redis-backed deployment, Gemini credential, or browser session was available.
2. **Public edit links are not E2EE:** the current HTTP server generates the snapshot key, plaintext authoritative elements remain in the database, and the share fragment does not encrypt the active JSON WebSocket protocol. Treat this as a product/security blocker for an E2EE claim; see [`docs/collaboration-crdt-e2ee-decision.md`](./collaboration-crdt-e2ee-decision.md).
3. **In-memory ticket/state limitations:** WS room state, HTTP WS tickets, and rate-limit fallback state are process-local. Horizontal scaling requires shared durable state and a real distributed test.
4. **Room model remains large:** `apps/ws-server/src/index.ts` still coordinates parsing, authorization, room state, persistence, Redis, presence, locks, and protocol handling. This raises regression risk even though pure helpers now have tests.
5. **Dependency audit is time-sensitive:** the audit was clean on 2026-09-25 after updates/overrides; re-run on every dependency change and in CI/release tooling.
6. **Image privacy model:** public capability downloads are necessary for shared canvases but mean an image ID is an access capability. Expiring/revoking image capabilities is not implemented.
7. **Snapshot capability storage:** public canvas snapshots still use a bounded process-local map. Valid links can be unavailable across instances/restarts, and a full map now returns capacity errors rather than silently evicting an existing link. Use durable shared storage before calling snapshots production-grade.
8. **Legacy migration compatibility:** a fresh PostgreSQL 16 database can apply the migration chain, but a populated database that has the initial migration and has not yet applied the historical password migration needs a reviewed preflight/manual repair because that old migration adds a non-null password column without a default. Do not claim a zero-downtime upgrade path until that compatibility procedure is exercised. See [`docs/database-migration-notes.md`](./database-migration-notes.md).
9. **Validation is not uniform:** room/file scene writes are schema-checked, but several `http-server/src/routes/auth.ts` handlers still use manual body checks; do not claim every HTTP input is Zod-validated.

## Collaboration correctness assessment

### Implemented and tested seams

- `useCollaboration` queues scene mutations while disconnected and replays them only after `sync_room_state`; stale pre-sync/previous-room snapshots are discarded, pending ticket requests are aborted/generation-guarded, and queued updates for elements absent from an authoritative reconnect snapshot are dropped conservatively. The client lifecycle tests cover ordering and stale-ticket/stale-deletion cases.
- Server-side room/file access is centralized in `roomAccess.ts`; share tickets are scoped to one file, current token, and permission, with authorization refreshed for mutations and a bounded passive sweep that closes revoked connections.
- Remote and local element updates use common version/`versionNonce`
  reconciliation with Excalidraw's lower-nonce tie-break; this is deterministic
  per-element selection, not evidence of CRDT convergence. Equal versioned
  payloads are not rebroadcast.
- Scene deltas, deletes, combined capacity limits, deduplication IDs, persistence generation checks, optimistic database fencing, and remote Redis application were tightened.
- Stored scene parsing validates elements and caps the room scene.

### Not yet proven

- The two-client process test boots
  `apps/ws-server/src/index.ts` with two real `ws` clients by default, but mocks ticket
  validation and persistence; it does not prove a PostgreSQL-backed deployment. (The old
  self-contained `integration.test.ts` protocol-model fixture, which modeled legacy
  `room-state` without importing any shipped source, was deleted 2026-09-28 after its
  unique flows — auth rejection, user-join, leave/close fan-out, element fan-out,
  scene-update relay, cursor both spellings, ping — were ported into the live suite.)
- No verified reconnect test covers authorization changes between disconnect and reconnect.
- Same-user multi-tab connection identity is not fully modeled; duplicate authenticated tabs are rejected rather than allowed to overwrite `room.users`, but a future connection-ID presence model is still needed for intentional multi-tab support.
- Yjs binary updates are intentionally disabled on the wire. JSON deltas are the active protocol and do not provide CRDT convergence under concurrent edits. Durable tombstones, accepted-operation acknowledgements/healing, and a room revision/sequencer remain open convergence work.
- The previous canvas worker was removed as dead/unwired code. The active `RoughCanvas` hit-test/render path uses a local RBush; browser behavior is not proven.
- Redis fan-out now applies remote mutations to the local room, but the load-then-subscribe gap, non-durable Pub/Sub, process-local presence/presence metadata, persistence ownership, and partition/reconnect behavior remain untested and block horizontal-scaling claims.
- A stale `updatedAt` fence still has no general WS rebase/authoritative reload path; the browser file editor now handles a safe retry or pauses with a reload action, but a production conflict/recovery test is still required.
- Shutdown now stops new messages, bounds final-save/close waits, and reports failed saves, but no real long-session drain or rolling-deployment test has been run.

## Persistence and sharing assessment

- File and room writes validate stored scene elements and reject malformed payloads.
- `FileService.updateFile` uses `updateMany` with `updatedAt` matching and returns a conflict instead of silently overwriting a newer scene.
- WS save scheduling captures a mutation generation so an in-flight write cannot clear newer dirty state.
- Share tokens are generated with CSPRNG and owner-scoped for creation. File-share tokens are rotatable/revocable and checked for expiry; room `ShareLink` records are owner-created and expire, but the current room API has no separate revoke endpoint.
- Image URLs use strict generated IDs and public capability downloads for shared scenes.
- File-share snapshots retain their encrypted payload across owner edits.
- `GET /api/rooms/share/:token` is public by capability token, and `/board/[token]` is explicitly a read-only preview. This is not the same as authenticated collaborative room editing.
- Share ticket storage is in memory; a multi-instance HTTP deployment can validate a ticket only on the instance that issued it.

## Final assessment

Dripl should be treated as a **strong feature prototype / early beta**, with meaningful implemented breadth and improving engineering controls.
